# ADR 0006 — Embeddings, pgvector, and RAG

## Status

Accepted

## Context

Phase 6 adds semantic similarity (`GET /events/:id/similar`) and grounded Q&A (`POST /ai/ask`). Rule-based tags cannot cluster paraphrases (Kafka docs vs RabbitMQ docs). Embedding API calls are slow and cost money; LLM answers hallucinate without retrieval.

## Decision

### Provider and models

- **Embeddings:** OpenAI `text-embedding-3-small` (1536 dimensions) behind `EmbeddingPort`
- **LLM:** OpenAI `gpt-4o-mini` behind `LLMPort`
- Adapters call the OpenAI HTTP API via `fetch` (no SDK dependency). When `OPENAI_API_KEY` is unset, fake adapters run for local/e2e.

### Vector store

- Store vectors in PostgreSQL with **pgvector** (`event_embeddings`)
- HNSW index with `vector_cosine_ops`
- Every similarity query **must** filter by authenticated `user_id` and matching `model`

### Async pipeline

- Embeddings are generated by `GenerateEmbeddingUseCase` on a dedicated BullMQ `embedding` queue
- Triggered from the same outbox `EventIngested` fan-out as tagging/projections
- `SubmitEventUseCase` never calls embedding or LLM APIs — ingest latency stays Phase-4 identical
- Idempotency: skip when `content_hash` + `model` already match

### RAG policy

- Retrieve top-K (default 8) with optional hybrid filters (`from`, `to`, `tags`)
- Empty or below-threshold retrieval → **refuse** (no LLM call); never silently drop filters
- LLM failure after retrieval → `mode: "snippets_only"` with citations
- AI routes rate-limited (~10 req/min)

### Cost envelope

- Prefer `text-embedding-3-small` over larger models
- Cap retrieval K and LLM `max_tokens`
- Rate-limit `/ai/ask`

## Consequences

- Requires `pgvector` (Docker image `pgvector/pgvector:pg16`)
- Changing embedding model/dimensions needs a migration and re-embed
- Similar/RAG degrade gracefully when embeddings are missing or OpenAI is down; tags and ingest remain available
